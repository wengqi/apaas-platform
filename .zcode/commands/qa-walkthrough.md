执行推送前 QA 走查（工作约定 2026-10-06），方法论加载 `browser-use:web-gui-tester` skill：

1. **确定范围**：本次变更影响的界面与功能点，对照 `docs/testing/QA-TEST-PLAN-PROMPT.md`
   清单与 `docs/testing/TEST-CASES.md` 对应用例，确定走查矩阵与检查深度。
2. **矩阵走查**：按 {草稿, 已发布} × {画布创建, API 创建} 覆盖受影响界面（不涉发布态的功能
   可裁剪维度，须说明理由）；主动构造真实数据走通交互，空列表不得作为跳过理由。
3. **二级交互必须实际执行**：弹窗/抽屉/详情/操作按钮等二级交互拆为独立检查项，操作到
   "结果可见"（数据变化/状态流转/渲染产物）；禁止以"入口可达/页面渲染/结构通过"替代
   （D-011 教训：二级弹窗交互盲区）。
4. **证据与全帧异常扫描**：每步验证截图留档 `gui-test-screenshots/`（文件名按场景编号）；
   截图后做全帧异常扫描——列出画面上所有状态标签，自问是否互相矛盾（如"未保存"标记 vs
   实际已保存、空态文案 vs 列表有数据）。
5. **e2e 冒烟**：`pnpm test:e2e:smoke`（核心旅程 5 个 spec）；注意与手工走查并发可能互踩
   登录限流（429），冒烟失败先隔离重跑再定性。
6. **产出报告**：通过点 / 问题点（按严重度，附证据截图路径）/ 《未执行清单》（无法执行的
   场景注明原因：外部依赖/权限/环境），与已测结论严格分离。
7. **问题处置**：High 必须当场修复并回归（补单测/GUI 复验）；Medium 默认修复；走查发现的
   体系性缺陷在同一提交内同步 `docs/testing/QA-TEST-PLAN-PROMPT.md` 与 `TEST-CASES.md`
   对应用例。

红线：通过结论必须基于当次实际反馈，禁止凭代码阅读或历史结论推断；执行口径不得因任务时长
或步骤复杂而降级，发现必须降级时立即报告并经用户确认。
