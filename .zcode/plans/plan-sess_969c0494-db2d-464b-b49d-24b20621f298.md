# 实施计划：修复 4 项阻断性技术债

## 概述

按 ROADMAP「后续推进建议」第一步，修复 TD-1 ~ TD-4 四项阻断性技术债，为新模块（P5/P6/P9）扫清前置依赖。代码审计已完成，以下为逐项实施方案。

---

## TD-1：权限强制执行（预计 ~1h）

**问题**：`PermissionGuard` 完整实现但未挂载到任何路由，所有控制器仅用 `JwtAuthGuard`，任何登录用户可访问所有 API。

**方案**：将 6 个业务控制器的 `@UseGuards(JwtAuthGuard)` 替换为 `@UseGuards(PermissionGuard)`，并给关键路由添加 `@RequirePermission()` 装饰器。权限检查采用**渐进式策略**——先给管理类路由（CREATE/EDIT/DELETE/MANAGE）加权限校验，查询类路由（VIEW）暂保持仅认证，避免因无权限规则数据导致全部 403。

### 修改文件

1. **各模块 module.ts**（6个：application/object/record/page/process + permission 自身）— import `PermissionModule`，使 `PermissionGuard` 可注入
2. **6 个控制器** — `@UseGuards(JwtAuthGuard)` → `@UseGuards(PermissionGuard)`，添加 `@RequirePermission` 装饰器：

| 控制器 | 路由 | 装饰器示例 |
|--------|------|-----------|
| `ApplicationController` | create/update/delete | `@RequirePermission('PAGE', 'MANAGE', 'appId')` (暂用 PAGE 维度) |
| `ObjectController` | create/update/delete Object + Field + View | `@RequirePermission('DATA_MODEL', 'CREATE/EDIT/DELETE')` |
| `RecordController` | create/update/delete | `@RequirePermission('RECORD', 'CREATE/EDIT/DELETE')` |
| `PageController` | create/update/delete/publish | `@RequirePermission('PAGE', 'CREATE/EDIT/DELETE')` |
| `ProcessController` | create/update/delete/start | `@RequirePermission('PROCESS', 'CREATE/EDIT/EXECUTE')` |
| `RoleController` / `OrgController` / `UserController` | 保持 `JwtAuthGuard`（权限管理本身仅限 ADMIN/BUILDER，由 superAdmin 短路覆盖） |

3. **`PermissionGuard`** — 修复一个逻辑 bug：当 `targetIdParam` 存在但路由参数中无对应值时，当前直接 `return true`（跳过检查），应改为仅检查类型+动作级权限或拒绝

### 验证
- `admin@apaas.dev` (superAdmin) 所有操作正常
- `builder@apaas.dev` (无 ADMIN 角色) 管理类操作返回 403（无权限规则时 default-deny）

## TD-2：BullMQ 异步队列（预计 ~2h）

**问题**：流程引擎同步执行，delay 节点 ≤60s（in-process setTimeout），无崩溃恢复。

**方案**：引入 BullMQ + Redis（Redis 已在 docker-compose 中运行），将 `ProcessEngine.executeNextNode` 改为队列驱动。delay 节点改用 BullMQ delayed job。

### 修改文件

1. **`apps/gateway/package.json`** — 添加 `bullmq` + `ioredis` 依赖
2. **新增 `apps/gateway/src/queue/queue.module.ts`** — BullMQ 队列模块，注册 `processQueue`，导出队列供注入
3. **新增 `apps/gateway/src/queue/process.processor.ts`** — BullMQ Worker，消费 `executeNextNode` job，调用 `ProcessEngine.executeNextNode(instanceId)`
4. **`ProcessEngine`** 修改：
   - `startProcess()` — 创建实例后，不再直接调 `executeNextNode`，改为 `processQueue.add('execute', { instanceId })`
   - `executeNextNode()` — 保持核心逻辑不变，但每次 token 推进后，若实例仍 RUNNING，再次 `processQueue.add`（异步链式推进）
   - `completeTask()` — 恢复执行也改为入队
5. **`DelayExecutor`** — 不再用 setTimeout，改为返回 `{ wait: true }` + 调度 BullMQ delayed job 在到点后恢复令牌（通过新方法 `ProcessEngine.resumeDelayedNode`）
6. **`ProcessModule`** — import `QueueModule`
7. **`app.module.ts`** — import `QueueModule`

### 验证
- 手动启动流程 → 节点异步执行 → 正常完成
- delay 节点 5s → BullMQ delayed job 到点恢复
- 实例 RUNNING 状态可在 DB 中观察到中间状态

## TD-3：runtime-ui 渲染引擎（预计 ~3h）

**问题**：`runtime-ui/src/pages/AppView.tsx` 为桩函数，搭建的应用只能在 Studio 预览模式运行。

**方案**：将 Studio 的 4 个渲染核心文件移植到 runtime-ui，新增 pages API + runtime 页面组件，实现独立渲染。不复制 `ComponentRenderer.tsx` 全部 1089 行编辑模式逻辑——只提取 preview 模式的渲染部分。

### 修改文件

1. **`packages/runtime-ui/src/api/`** — 新增：
   - `pages.ts` — 页面 API（list/get/getBySlug），类型从 studio 复制精简版
   - `objects.ts` — 对象记录 API（records.list/create/update/delete）
2. **`packages/runtime-ui/src/runtime/`** — 新增（从 studio 移植）：
   - `expression-engine.ts` — 完整复制（194行，无 studio 耦合）
   - `action-executor.ts` — 完整复制（323行，仅依赖 antd + objectsApi）
   - `RuntimeStore.tsx` — 完整复制（284行，仅依赖 react + objectsApi + action-executor）
   - `ComponentRenderer.tsx` — 精简复制：只保留 preview 模式渲染逻辑，移除 edit 模式的 dnd-kit / 选择边框 / 悬浮工具栏（约 600 行）
3. **`packages/runtime-ui/src/pages/AppView.tsx`** — 重写：加载应用已发布页面列表 → 点击进入页面渲染
4. **新增 `packages/runtime-ui/src/pages/PageView.tsx`** — 运行时页面渲染器：加载页面 Schema → RuntimeStoreProvider → ComponentRenderer 递归渲染
5. **`packages/runtime-ui/src/router.tsx`** — 添加路由 `/app/:appId/p/:slug` → `PageView`
6. **`packages/runtime-ui/src/pages/TaskCenter.tsx`** — 对接流程任务 API（listTasks/completeTask/delegateTask），复用 studio 的 ProcessMonitor 任务处理逻辑

### 后端补充
7. **`page.controller.ts`** — 新增 `GET /api/apps/:appId/pages/slug/:slug` 路由，调用已有的 `pageService.getBySlug()`（后端已实现但未暴露）

### 验证
- Studio 中搭建列表页 → 发布 → runtime-ui `/app/:appId/p/:slug` → 页面正常渲染 + 数据加载
- 表单提交 → 记录创建成功
- 任务中心 → 待办列表 → 审批

## TD-4：自动触发器（预计 ~1.5h）

**问题**：流程仅能手动启动，无法响应记录事件/定时调度。

**方案**：实现 record_event 触发器（最常用类型）。在 `RecordService` 的 create/update/delete 后触发匹配的流程。schedule 触发器用 BullMQ repeatable job（依赖 TD-2）。

### 修改文件

1. **新增 `apps/gateway/src/process/trigger.service.ts`** — 触发器服务：
   - `onRecordEvent(tenantId, appId, objectId, eventType, recordData)` — 查找 `triggerType = RECORD_CREATED/UPDATED/DELETED` 的已发布流程定义，调用 `ProcessEngine.startProcess` 传入触发上下文
2. **`RecordService`** — 注入 `TriggerService`（可选注入避免循环依赖），在 `create()` / `update()` / `delete()` 后调用 `triggerService.onRecordEvent()`
3. **`RecordModule`** — import `ProcessModule`（或通过 forwardRef 解决循环依赖）
4. **`ProcessModule`** — export `TriggerService`
5. schedule 触发器：在 `QueueModule` 中注册 BullMQ repeatable job，定期扫描 `triggerType = SCHEDULED` 的流程定义并触发

### 验证
- 创建流程定义 triggerType=RECORD_CREATED → 发布
- 创建记录 → 流程自动启动 → 实例 RUNNING
