# ADR-0003: 产品方向修订 — 受约束的 AI 应用生成底座（Schema 优先 + amis 单方言）

- 状态：已接受
- 日期：2026-09-30
- 关联：ADR-0002（本 ADR 修订其 AI 排除条款与优先级排序）、`docs/design/DESIGN-refactor-blueprint-2026-09-30.md`（重构蓝图）、`docs/knowledge-base/OSS-SELECTION-VERIFICATION-2026-09-30.md`（选型证据）、`docs/research/RESEARCH-feishu-apaas-live-benchmark-2026-09-27.md`

## 背景

1. **表单/页面模块的反复缺陷是结构性问题**。2026-09-29 代码勘察实锤：86 组件渲染矩阵没有显式"属性合同"——属性面板写入的字段名 ≠ 渲染器读取的字段名（同口径 bug 一次实测爆发 9 个且仍有活体）；87 个渲染函数零单元测试，质量靠人工全组件浏览器实测兜底；ComponentType 在 4 个文件重复声明，新增组件需 7-9 处手工同步。根因判定为**产品重心放错层**：~37k 行投在搭建器 UI，而真正决定平台价值的元数据/治理层（Schema 合同、版本模型、环境隔离）反而是最薄弱部分。
2. **行业信号**（2026-09 调研）：AI 生成应用成为平台级共识——NocoBase 定位已改为"AI + no-code platform"，OpenTiny 活跃开发已转向 genui-sdk/webmcp-sdk；2020-2022 一代"渲染器/引擎类"中文 OSS（amis/formily/lowcode-engine）集体进入静默期，佐证拖拽搭建时代的势能转移。ADR-0002 当时排除 AI 的前提（先做好基础设施）仍然正确，但结论需要升级：**基础设施的正确性标准应以"AI 将消费它"重审——Schema 合同与治理轨道正是 AI 可控性的实现机制**。
3. **维护量级确认：2 人小组 + AI 自主**。79k 行自研代码按历史缺陷密度（近 30 个 commit 中 18 个在修搭建器）不可持续，必须按"自建差异化内核 + 商品层换开源"切割。
4. **选型经直接核实**（查源码仓库/npm registry/commit 记录/官方定价页，详见知识库核实记录）：amis 渲染器+编辑器全源码在主仓库（Apache-2.0 / amis-editor-core npm 标注 ISC，无发布限制），维护放缓（末 release 2025-08、末 commit 2026-03）；formily 自 2025-06 起事实停更；NocoBase 为"开源核心+商业版本"模式，SSO/高级审批流/环境隔离均在 $8,000 Professional 付费墙内；lowcode-engine 事实停滞。

## 决策

1. **产品论**：平台 = **受约束的 AI 应用生成底座**。元数据（对象/流程/权限/环境/版本）与治理轨道是产品本体；**AI Agent 为第一公民用户**（经 Schema/MCP 接口生成与修改应用），企业开发者第二（代码逃生舱：自定义组件/节点/云函数），拖拽搭建降级为人工兜底手段。
2. **修订 ADR-0002 决策 3/6**：撤销"AI 生成页面/流程、MCP Server 暂缓/不做"条款 → AI 一等公民（R1.6/R1.7）。**治理闸门 = 全环境人审**：AI 产出仅进草稿，任何环境发布必须人工审批；R1.2 版本模型按"AI 出稿、人审批"设计，验收重心为 **diff 快审**（schema 级 diff、按对象/流程/页面变更粒度、一键批准/驳回）——AI 可控性的三层机制中，运行时权限层（ABAC 条件下推+租户隔离+审计）已是自研资产，本次补齐 Schema 合同层与治理轨道层。
3. **界面层 = amis 单方言三用法**（不引入 formily）：① 流程表单（amis form，`static` 只读态=审批查看，73 种表单控件 + 显隐联动 + 双层校验覆盖审批场景）；② AI 生成页面（amis page，吃 LLM 语料红利）；③ 拖拽兜底编辑器（现有搭建器 amis 化改造）。**PageSchema v2 采用 amis 方言**，存量 v1（仅 demo 应用与 e2e，首个真实应用尚未交付，存量≈0）一次性迁移，不做渐进兼容。
4. **应用三形态**：纯页面 / 流程+页面 / 纯流程（headless：API 触发器 + API Key/服务身份 + 流程版本稳定性承诺——外部系统对接 v1 时，平台发布 v2 不得破坏 v1 契约，与 R1.2 版本模型绑定）。
5. **底座自建瘦身**（不采用 NocoBase 底座，仅作架构参照 + Plan B）：自研 86 组件渲染矩阵换 amis、数据集引擎下沉 PostgreSQL（SQL 聚合/物化）、页面双渲染器合一、组件 86→约 30 核心集；**流程引擎、权限内核（ABAC 下推）、对象模型、身份层保留并加强**；目标自研代码 ~50k 行。NocoBase 付费墙功能（SSO/审批语义/环境隔离）恰为本项目自研强项与 P0 清单，换底座等于付费买回已拥有的东西。
6. **优先级重排**：R1.3 升 P0 首位，首个验收应用场景锁定**采购合同类流程审批**（金额条件分支/多级顺序审批/会签或签/加签转办撤回/流程表单/流程出入参/合同附件与台账）——验收应用是界面形态为"流程+页面"类，**不需要页面搭建器**，因此 P0 只需 amis 表单通道；页面层整页化列为 R1.7（P2）。新增前置 spike（P0 准入门槛）：amis antd 主题视觉贴合度实测、LLM 生成 amis schema 合法率对比。

## 后果

- 正面：单一方言从土壤上消除"属性合同"类缺陷（渲染合同由 amis 的成熟契约承接）；AI 语料红利 + Schema 校验合同使 AI 生成可控可审；2 人维护面减半（渲染矩阵/数据集引擎/双渲染器移出自研清单）；验收应用与 R1.3 深度互相锚定，重构与首个真实应用交付合二为一。
- 负面/代价：amis 维护放缓（末 commit 2026-03）→ 锁定版本 + fork 预案；amis antd 主题视觉贴合度待 spike 实证；自有绑定/动作语义（vm 数据域、13 动作类型）需适配层；全环境人审要求审核 UX 高效，否则 2 人小组被审核队列淹没（diff 快审列为 R1.2 验收项）。
- 明确不做：formily（2025-06 起停更，其深度字段联动优势在审批表单场景用不上，极端复杂动态表单走 amis 自定义 React 组件逃生舱）；NocoBase 底座替换（理由见决策 5）。
