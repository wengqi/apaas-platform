# ADR-0004: AI 底座阶段方向校准 — 开发者优先维持、studio 结构性保障、遥测驱动

- 状态：已接受
- 日期：2026-10-09
- 关联：ADR-0003（本 ADR 校准其决策 1/5 的表述并补全治理与质量机制，不推翻其产品论）、`docs/design/DESIGN-refactor-blueprint-2026-09-30.md`（瘦身清单校准注记）

## 背景

ADR-0003 执行约十天内（2026-09-30 ~ 2026-10-08），AI 主线四轮（R1 打磨 / R2 报表 / R3 数据集 / R4 权限工具面）实测闭环，"表单+审批+报表"首要成功标准三条腿全部在真实生成的应用上走通。据此对产品方向与系统设计做了一轮结构化压力测试讨论（12 项裁决），暴露三个 ADR-0003 未裁决的张力：

1. **AI 自主性 vs 全环境人审**：治理闸门使每次 AI 提交必过人，批次提交（2 调用 1 人审）是缓解非解法；规模化后审核队列是第一瓶颈，且当前没有任何度量（首过率 / G3 拦截原因 / 驳回原因 / 返工轮次均不可知），打磨全凭手感驱动。
2. **瘦身叙事 vs AI 主线增重**：蓝图三项具名瘦身裁剪已完成（79.6k→61.5k，见蓝图瘦身清单），但 R2-R4 的 MCP 工具面/治理模块/校验器实增约 8.5k（实测约 70k 量级），50k 目标剩余缺口无具名裁剪对象，数字锚事实上失锚。
3. **studio 定位**：ADR-0003 将拖拽搭建"降级为人工兜底"，但 studio（~31.4k 行，最大包）持续深度打磨（字段绑定/撤销重做/图标），字面表述与投入现实相悖。

## 决策

1. **目标用户校准：开发者优先维持**。AI 是开发者的交付工具，不是替代开发者向非开发者转型——"企业内部真实使用"的完成主体仍是开发者（与 ADR-0002"先开发者后业务"一致）。校准 ADR-0003 决策 1 中"企业开发者第二"的表述：第二的是**交付顺位**（AI 出稿、人审把关），不是目标人群。
2. **AI 形态澄清：外部 agent，平台不内置**。开发者经外部编码 agent（ZCode/Claude 等）通过 MCP 接入，平台本身不做内置 AI 对话框/助手（底座不做 LLM 应用）。"开发者体验"的投入面 = MCP 工具面、方言指南、错误信息可读性，不含平台内 chat UI。
3. **studio 定性修正：AI-first 的结构性保障，非弃养兜底**。studio 承担两个不可替代角色：① AI 生成界面的人工二次修改能力（"兜底"的本义）；② 方言可行性证明器——人工能拖出的界面才证明 amis 方言表达得了，AI 生成质量以此为锚。其投入与 AI 主线同向，不设投入限制规则。
4. **二次修改工作流前移（草稿可改流）**：现状 AI 草稿（PENDING）人审只能批/驳二选一——批准后才能改，驳回则整体打回，中段路径缺失。新增"草稿可改"：人审前开发者可在 studio 打开 PENDING 草稿微调，人工修改后的草稿按既有规则视为人工提交（即时 APPROVED，保留版本谱系，兼容批次拓扑）。列入下一轮主线实现。
5. **AI 生成遥测立为 P0**：观测事件 SSOT 四分类扩为五分类（新增 AI_GENERATION），携带方言类型 / 校验拦截规则码 / 返工轮次 / 驳回原因等结构化维度；指标口径：以 batchId 为单位算一次人审通过率，以资源为单位算 G3 首拦率，返工轮次按 batchId 链上重提次数计。治理类机制（信任升级等）一律缓行至遥测数据可用。
6. **瘦身目标校准：撤销 ~50k 数字锚**。保留"删旧优先"结构性原则，不再设自研行数总量目标；AI 底座的工具面/治理/校验属合理增重。蓝图瘦身清单视为已完成的战役（追加校准注记）；自研行数目标以本 ADR 为现行权威（带日期快照文档如 PLATFORM-OVERVIEW 不回改）。
7. **AI interface 质量机制两项**（系统设计决议）：
   - **方言指南 ↔ G3 校验器一致性测试**：四份方言指南（amis/workflow/dataset/permission）中每条校验器拒绝规则必须有对应说明（反向亦然），使 #21 类指南漂移（指南教错契约→AI 照错→G3 拦下→返工一轮）成为 CI 可拦截项。最小做法，不做指南生成管线。
   - **JsonLogic 可译子集统一定义**：权限侧 `shared/jsonlogic-to-prisma.ts`（strict、fail-closed）与数据流侧 `dataset/jsonlogic-to-sql.ts`（可译子集、返回 null 兜底）**不合并实现**（失败语义相反是设计使然），但在 `packages/shared` 抽共享的"可译子集"定义 module（操作符白名单 + 操作数类型契约），两个翻译器消费同一份定义并各自以单测锚定支持范围——消除"同一条件两处行为不同"的双事实标准。
8. **下一轮主线**：数据驱动的 AI 生成质量第一轮——落遥测（决策 5）+ 以开发者身份实测交付第二个真实应用（候选：员工报销，覆盖表单/多级审批/行级权限/报表）+ 据遥测数据修方言指南与校验器。

## 后果

- 正面：三个张力全部有归属（人审瓶颈→遥测供数后裁决；瘦身→原则化；studio→同向定性消解）；"AI 生成+人工二次修改"从概念变为有落地件的工作流（决策 4）；AI 打磨从手感驱动转向数据驱动（决策 5）。
- 负面/代价：草稿可改流扩大治理面（PENDING 状态可被人工编辑），需在版本谱系与批次拓扑上补测试；遥测与一致性测试均为纯投入项，短期无用户可见功能。
- 明确不做：内置 AI 对话助手；信任升级机制（遥测数据出来前不考虑）；JsonLogic 两翻译器的实现合并；50k 行数锚的继续追账。
