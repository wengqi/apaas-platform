## 1. 设计概述

### 1.1 定位

权限模块是 aPaaS 的「治理层中枢」。用户在此定义角色、搭建组织架构、分配用户,并对每个角色配置五级权限(页面 / 记录 / 流程 / 数据模型 / 连接器)。运行时由权限引擎根据「用户 → 角色 → 权限规则」三元关系做访问控制,记录级条件权限提供行级数据隔离。本模块遵循「元数据驱动」——编辑器产出的是 `PermissionRule[]` 配置 JSON,而非代码。

四大核心概念(来自 `packages/shared/src/permission/index.ts` + Prisma):

| 概念 | 类型 / 模型 | 说明 |
|---|---|---|
| 角色 | `Role` | `appId` 为空=租户级,非空=应用级;`isBuiltIn` 标记内置角色 |
| 组织节点 | `OrgNode` | 树形(`parentId` 自关联),`nodeType`: department / team / position |
| 权限规则 | `PermissionRule` | `type`(五级)+ `action`(六动作)+ `targetId` + `condition?`(行级条件) |
| 用户-角色 | `UserRole` | 多对多关联表(角色成员) |

### 1.2 五级权限体系

对齐飞书 aPaaS 五级权限 + 四级粒度:

| 权限类型 (`PermissionType`) | 控制对象 | 粒度 | 可配动作 (`PermissionAction`) |
|---|---|---|---|
| 页面权限 `page` | 应用内页面 | 页面级 | `view`(可访问)、`manage`(管理) |
| 记录权限 `record` | 对象记录 | 表级 + 行级(条件) + 列级(字段) | `view`、`create`、`edit`、`delete` |
| 流程权限 `process` | 流程定义 | 流程级 | `execute`(可发起)、`manage` |
| 数据模型权限 `data_model` | 对象 + 字段 | 表级 + 列级 | `view`、`create`、`edit`、`delete` |
| 连接器权限 `connector` | 连接器 / 函数 | 资源级 | `execute`(调用)、`manage` |

> 行级权限 = `PermissionRule.condition`(条件表达式);列级权限 = 数据模型权限的字段级配置;人员级权限 = 条件中引用「当前用户 / 当前部门」等动态上下文值。

### 5.4 值类型与动态上下文值

| 值类型 | 控件 | 产出 |
|---|---|---|
| `literal` 字面量 | 按字段类型(文本 `Input`、单选 `Select`、数字 `InputNumber`、日期 `DatePicker`、多选 `Select multiple`) | `{ kind:'literal', value }` |
| `context` 动态值 | `Select`,候选见下表 | `{ kind:'context', context }` |
| `field` 字段比较 | `Select`(候选 = 同对象其他字段) | `{ kind:'field', field }` |

**动态上下文值候选**(人员级权限核心):

| context | 显示名 | 适用字段类型 | 语义 |
|---|---|---|---|
| `current_user` | 当前用户 | User / 文本(用户ID) | `字段 = 当前登录用户 ID` |
| `current_user_depts` | 当前用户所在部门 | 文本(部门ID)/ 单选(部门) | `字段 ∈ 当前用户的部门 ID 集合` |
| `current_user_roles` | 当前用户的角色 | 文本(角色ID) | `字段 ∈ 当前用户角色 ID 集合` |
| `supervisor` | 当前用户的上级 | User | `字段 = 当前用户的主管` |
| `record_owner` | 记录创建人 | User | (用于跨字段比较,等同 `created_by`) |

> `is_empty` / `is_not_empty` 操作符时隐藏值输入。

### 5.5 嵌套条件组

- 「+ 添加条件组」:递归渲染同一组件,子组有自己的 `logic`(AND/OR),`conditions[]` 可含子组
- 数据结构对齐对象视图 `ViewFilterGroup`,扩展 `value` 为 `ConditionValue` 联合类型(见 §11.3)

### 5.6 序列化与预览

- 保存:将 `RecordCondition` 树序列化为 JSON 字符串,存入 `PermissionRule.condition`
- 预览区:遍历条件树生成类 SQL 文本(动态值用 `{{currentUser}}` 等占位),实时更新
- 常用模板:点击直接填充条件树(「仅看自己负责的记录」→ `负责人 eq context:current_user`)

### 5.7 多动作条件

顶部 `Select`:「查看」/「编辑」。分别为 `view` / `edit` 动作配置独立条件(存为两条 `PermissionRule`,action 不同)。默认「查看」。

### 11.2 数据模型扩展(Prisma)

`PermissionRule` 类型已定义但未持久化。建议扩展 `Role` 模型:

```prisma
model Role {
  // ... 现有字段
  /** 权限规则 JSON:PermissionRule[](type/action/targetId/condition) */
  permissionRules Json @default("[]") @map("permission_rules")
  /** 角色启用状态(关闭后不参与权限计算) */
  enabled Boolean @default(true)
}
```

> 与 `workflow_schema` / `view.config` 的 JSON 存储模式一致,首期以 JSON 存规则足够。若需按规则高频查询(如运行时鉴权),可后续拆为独立 `PermissionRule` 模型:
> ```prisma
> model PermissionRule {
>   id String @id @default(cuid())
>   roleId String
>   type String   // page|record|process|data_model|connector
>   action String // view|create|edit|delete|execute|manage
>   targetId String
>   condition String? // 行级条件 JSON 字符串
>   role Role @relation(fields: [roleId], references: [id], onDelete: Cascade)
>   @@index([roleId]) @@index([type, targetId])
> }
> ```

组织授权扩散需新增部门-角色关联:

```prisma
model OrgRole {
  orgId String @map("org_id")
  roleId String @map("role_id")
  org OrgNode @relation(fields: [orgId], references: [id], onDelete: Cascade)
  role Role @relation(fields: [roleId], references: [id], onDelete: Cascade)
  @@id([orgId, roleId]) @@map("org_roles")
}
```

> `OrgNode` 需补 `orgRoles OrgRole[]`、`Role` 需补 `orgRoles OrgRole[]` 关系。审计日志新增 `AuditLog` 模型(P2)。

### 11.3 类型声明(条件构建器)

记录级条件权限的条件结构,扩展对象视图 `ViewFilterGroup`:

```ts
/** 条件值(支持字面量/动态上下文/字段比较) */
export type ConditionValue =
  | { kind: 'literal'; value: unknown }
  | { kind: 'context'; context: 'current_user' | 'current_user_depts' | 'current_user_roles' | 'supervisor' }
  | { kind: 'field'; field: string };

/** 记录级条件(扩展 ViewFilterCondition,值可为 ConditionValue) */
export interface RecordCondition {
  field: string;
  operator: FilterOperator;
  value?: ConditionValue;
}

/** 条件组(AND/OR,可嵌套) */
export interface RecordConditionGroup {
  logic: 'AND' | 'OR';
  conditions: (RecordCondition | RecordConditionGroup)[];
}
```

> 序列化为 JSON 字符串存入 `PermissionRule.condition`。运行时由权限引擎解析为 SQL/查询过滤(动态值替换为当前用户上下文)。

### 11.6 API 封装(`api/permissions.ts`)

Studio 不直接依赖 `@apaas/shared`,按 `objects.ts` 惯例重新声明(对齐 `packages/shared/src/permission/index.ts`),ID 统一用 string:

```ts
export type PermissionType = 'page' | 'record' | 'process' | 'data_model' | 'connector';
export type PermissionAction = 'view' | 'create' | 'edit' | 'delete' | 'execute' | 'manage';
export type OrgNodeType = 'department' | 'team' | 'position';
export type UserStatus = 'ACTIVE' | 'DISABLED';

export interface Role {
  id; appId?; name; code; description?; icon?; isBuiltIn; enabled; permissionRules: PermissionRule[]; memberCount?; createdAt; updatedAt;
}
export interface PermissionRule { type: PermissionType; action: PermissionAction; targetId: string; condition?: string; }
export interface OrgNode { id; parentId?; name; code; nodeType: OrgNodeType; sort; children?: OrgNode[]; memberCount?; }
export interface User { id; email; name; avatar?; status: UserStatus; roles?: Role[]; orgs?: OrgNode[]; createdAt; }
export interface AuditLog { id; actorName; action; targetType; targetName; result; ip?; traceId?; payload?; createdAt; }

export const permissionsApi = {
  roles: {
    list(appId), get(roleId), create(appId, data), update(roleId, data), delete(roleId),
    listMembers(roleId), addMembers(roleId, userIds[]), removeMember(roleId, userId),
    updateRules(roleId, rules: PermissionRule[]),
  },
  org: {
    getTree(), get(orgId), create(data), update(orgId, data), delete(orgId), move(orgId, newParentId, sort),
    listMembers(orgId), addMembers(orgId, userIds[]), removeMember(orgId, userId),
    listAuthorizations(orgId), setAuthorizations(orgId, roleIds[]),
  },
  users: {
    list(params: { keyword?; status?; orgId?; page; pageSize }), get(userId),
    create(data), update(userId, data), setStatus(userId, status), resetPassword(userId),
    assignRoles(userId, roleIds[]), assignOrgs(userId, orgIds[]),
  },
  audit: { list(params: { type?; result?; start?; end?; page; pageSize }) },
};
```

> 路由风格对齐 `objectsApi`:`/api/apps/${appId}/roles`、`/api/roles/:roleId`、`/api/orgs/...`、`/api/users/...`。权限规则更新 `PUT /api/roles/:roleId/rules`(整体替换)或 `PATCH` 增量。

```
2. 新建根部门「飞书科技」→ 新建子部门「销售部」「研发部」(TreeSelect 选上级)
3. 拖拽调整:把「华东大区」拖到「销售部」下
4. 选中「销售部」→ 中栏「+ 添加成员」→ 选张三、李四、王五
5. 右栏「配置权限」→ 部门授权:添加「销售经理」角色
   └ 销售部(含子部门华东/华南)所有成员继承「销售经理」权限
```

### 12.3 权限计算规则(运行时,供前端预览参考)

```
用户最终权限 = 所有角色权限 ∪ 组织继承权限
  ├ 直接角色:userRoles → role.permissionRules
  ├ 组织继承:user.orgs → orgRoles → role.permissionRules(含上级部门继承)
  └ 行级过滤:record 类型规则的 condition 求值(动态值替换当前用户上下文)
字段可见性 = record.字段级 ∩ data_model.字段级(取交集,最严格)
权限动作:同 type+targetId 的多个 action 取并集
```
