# 重构蓝图 — AI 原生底座（P0 流程+表单闭环 / P1 治理轨道 / P2 页面层整页化）

- 日期：2026-09-30
- 依据：ADR-0003（`docs/adr/0003-ai-native-schema-first-platform.md`）
- 关联：全平台架构总览（双端/租户/环境/版本谱系/权限/部署）见 `docs/architecture/ARCHITECTURE.md`（2026-09-30 全量修订版）
- 性质：方向蓝图。各阶段工程实施须另行立项批准；本文档固化共识、阶段边界、准入门槛与风险登记。

## 目标态架构（三层）

```
┌─ 界面层（amis 单方言三用法）────────────────────────────┐
│ ① 流程表单：amis form（static 只读态=审批查看）          │
│ ② AI 生成页面：amis page（LLM 语料红利方言）             │
│ ③ 拖拽兜底编辑器：现有搭建器 amis 化改造（冻结新特性）    │
├─ 生成层（两类用户）───────────────────────────────────┤
│ AI Agent：MCP/Schema 接口 → 只产出草稿 → 全环境人审闸门  │
│ 企业开发者：代码逃生舱（自定义组件/节点/云函数/REST API）│
├─ 底座层（产品本体，自建保留并加强）─────────────────────┤
│ 对象/记录（JSONB 宽表+GIN）· 流程引擎+审批语义 ·         │
│ 权限内核（ABAC 下推）· 身份对接（CAS/LDAP）·             │
│ 版本模型（草稿→提交→发布，diff 快审）· 多环境 · 审计     │
└──────────────────────────────────────────────────────┘
```

应用三形态：纯页面 / 流程+页面 / 纯流程（headless：API 触发器 + API Key/服务身份 + 流程版本稳定性承诺）。

## P0 — 流程+表单闭环（验收应用主干）

> 首个验收应用 = 采购合同类流程审批，界面形态"流程+页面"，**不依赖页面搭建器**。

| # | 任务 | 说明 |
|---|------|------|
| S1 | **前置 spike ×2（P0 准入门槛）** | ① amis antd 主题视觉贴合度实测（关键页面截图对比）；② LLM 生成 amis schema 合法率 vs 自有 PageSchema 对比（同一需求，多轮采样）。任一不过 → 回到 ADR-0003 重新评估 |
| S2 | amis 渲染器接入（表单域先行） | runtime 引入 amis（锁版本），流程表单 schema = amis form；数据域绑定 vm.record；static 只读态承接"审批查看"，补录态=可编辑 |
| S3 | R1.3 审批语义补齐 | 审批人分环境配置、**会签/或签/依次**、加签/转办/撤回、审批结果变量；**流程表单**：user_task 节点绑定表单 schema（保存草稿按钮）；**流程出入参** |
| S4 | 采购合同应用骨架 | 对象建模：供应商/合同/审批台账（合同附件=attachment 字段）；流程：提交→金额条件分支→多级顺序审批（含会签节点）→归档→通知；台账页面+简单报表 |
| S5 | e2e 验收链路 | 验收应用全链路：表单提交→条件分支路由→会签/或签行为→撤回/加签→归档→台账/报表可见 |

**P0 验收口径**：S5 e2e 全绿 = R1.5 验收应用达成；R1.3 全部语义有单测。

## P1 — 治理轨道（AI 可控性）

| # | 任务 | 说明 |
|---|------|------|
| G1 | R1.2 版本模型（按 AI 出稿人审批设计） | 草稿→提交→发布三级；发布主体含 AI（AI 仅产草稿）；**验收项=diff 快审 UX**：schema 级 diff 视图、按对象/流程/页面变更粒度、一键批/驳 |
| G2 | R1.4 多环境 | dev/prod 按 environmentId 隔离；发布=切版本指针；触发器随版本启停（已有设计稿） |
| G3 | Schema 校验合同 | 三类 schema 的 JSON Schema 校验器：amis（表单/页面）、WorkflowSchema、对象元数据；**校验失败=AI 提交被拒**（合同层拒非法元数据） |
| G4 | R1.6 AI 生成接口（MCP） | 暴露对象/流程/页面/表单的读写与草稿提交；写入路径走 G3 校验 + G1 治理轨道；权限沿用 ABAC 内核（AI 生成的应用跑在同一权限内核里） |
| G5 | 并行小项：数据集引擎下沉 SQL | 聚合/物化改 PostgreSQL（GROUP BY/物化视图），删除内存 join（~2.5k 行），消灭卡死类 bug |
| G6 | 纯流程形态 API 产品化 | API 触发器 + API Key/服务身份 + 流程版本稳定性承诺（v1 契约不因 v2 发布破坏，依赖 G1） |

### G3/G4 补充：AI 生成的执行形态与规范传导

**执行位置**——AI 推理与 agent 循环不落平台，平台只新增 gateway 内的 MCP Server transport（无新增部署单元），认证走 G6 API Key/服务身份，审计记录操作者身份：

```
外部工具（Claude Code / Cursor 等任意 MCP 客户端）｜LLM 推理在供应商侧
  agent 循环：读元数据 → 生成 schema → submit_draft → 读错误 → 自修正
                    │ MCP（HTTP/SSE transport，G6 API Key/服务身份认证）
                    ▼
平台内（MCP Server 挂 gateway，不新增部署单元）
  G3 Schema 校验器 ── 非法：结构化错误返回 agent 自修正
       │ 合法
       ▼
  草稿 + 待审通知 ──▶ G1 审核中心（diff 快审）──▶ 人批 ──▶ 发布
```

**界面与分界线**：现阶段生成界面 = 外部工具自身 UI（定位"先开发者后业务"——开发者住在 IDE 里，IDE 级 agent 的"读→生成→修错"循环能力最强；自建对话界面与 agent 编排是最不划算的自研项，明确不做）。**生成在平台外，审核与发布永远在平台内**：产出回到 G1 审核中心看 schema diff、人批后才发布。未来若面向业务用户做平台内置对话面板，它只是又一个 MCP 客户端，复用同一套工具/校验/治理轨道（有意推迟到 P1 之后）。

**规范传导四层机制**——外部工具对我们的规范"连接时自动获知（2/3/4），提交时强制服从（1）"，不依赖模型恰好训练过 amis 或自有方言：

1. **校验反馈闭环（最硬的一道）**：`submit_draft` 即时校验，非法返回结构化错误（哪个字段/什么类型/违反哪条），agent 读错自修正重提。模型不需要背规范，只需要一个快速报错的循环——校验器即编译器，报错即教学，合法率随回合收敛。
2. **工具参数即合同**：MCP 工具自带参数 JSON Schema（如 `create_page(schema)` 的参数描述写明必填字段与类型），模型决定调用时第一眼看到的就是规范。
3. **规范文档作为 MCP Resources 下发**：amis 适配约定、vm 数据域绑定规则、WorkflowSchema 说明、四类元数据 JSON Schema 全文注册为 Resources，客户端按需拉取进上下文。
4. **服务端 few-shot 与示例**：MCP Prompts 提供任务模板（如"生成审批表单页"标准提示词）；平台现存合法 schema（模板库/验收应用）作为只读资源暴露——模型照对的例子写。

**完整回合示例**：开发者配置 `.mcp.json` 后输入"给采购合同应用加合同台账页（金额列/状态筛选/月度统计卡）" → agent 读对象元数据与页面示例 → 生成 amis page schema → `submit_draft` → 校验器发现绑定字段 `amt` 不存在并返回候选 `amount` → agent 修正重提通过 → 进草稿并通知待审 → 开发者在审核中心看 diff（新增 1 页面 + 1 数据请求）一键批准 → 发布。

**依赖顺序**：G3 必须先于 G4——没有合同，外部工具无从"知道规范"；没有 MCP，合同只能约束平台内编辑器。

## P2 — 页面层整页化（R1.7）

| # | 任务 | 说明 |
|---|------|------|
| W1 | amis page 整页渲染 | PageSchema v2 = amis 方言（页面级）；runtime-ui 整页切 amis 渲染 |

## 风险登记

| 风险 | 等级 | 缓解 |
|------|------|------|
| amis 维护放缓（末 commit 2026-03） | 🟡 中 | 锁定版本；fork 预案（Apache-2.0/ISC 无法律障碍）；表单/页面渲染为稳定领域，演进需求低 |
| amis antd 主题贴合度不达标 | 🟡 中 | S1 spike 为准入门槛，不过则回 ADR-0003 重议 |
| LLM 生成 amis schema 合法率低 | 🟡 中 | S1 spike 量化；G3 校验器兜底 + few-shot 示例库 |
| 2 人审核吞吐不足（全环境人审） | 🟡 中 | G1 diff 快审 UX 为验收项；变更粒度化 |
| 存量 e2e 迁移工作量 | 🟢 低 | 存量≈0（demo+e2e），一次性迁移 |
| 多副本部署 Redis 锁未压测（既有遗留） | 🟡 中 | 维持原风险项，P1 多环境落地前补压测 |

| 处置对象 | 规模 | 去向 |
|----------|------|------|
| 86 组件渲染矩阵 + 双渲染器 | ~12k | 换 amis 渲染器（P0 表单域/P2 整页） |

| 页面搭建器属性面板/组件注册 | ~4k | P2 重写为 amis setter（口径合同化） |
| 保留并加强 | 流程引擎+审批语义 / 权限内核 / 对象模型 / 身份层 / 治理轨道 | 差异化内核 |

**依赖新增规则**（项目红线）：amis 等新依赖逐个说明理由、更新 lockfile、PR 标注用途；不引入 formily。

## 明确不做

- formily（ADR-0003 决策）
- NocoBase 底座替换（作架构参照 + Plan B）
- AI 无审核直接发布（全环境人审为硬闸门）
