# 测试旅程地图 — 核心用例保整体正确（活文档）

> 创建：2026-10-06；同日扩充为完整影响矩阵并补齐三缺口。回答的问题：
> "模块很多且互相关联，改一处后，跑哪些用例能确信整体流程没坏？"
> 定位：**冒烟旅程保脊柱，单测保器官，全量 e2e 在 CI 兜底**——三层各司其职。

## 一、核心旅程（平台脊柱 + 第二环）

| # | 旅程（用户故事一句话） | 覆盖 spec | 串联模块 |
|---|---|---|---|
| J1 | 我能登录，租户之间互相看不见 | e2e/01-auth | auth、租户隔离 |
| J2 | 我能建模对象、增删改查记录 | e2e/02-object-crud | object、record（JSONB 宽表） |
| J3 | 提交→触发→多模式审批→批准归档 | e2e/16-procurement-approval | record 触发、流程引擎、会签/或签/依次聚合 |
| J4 | 驳回→状态回写→申请人收到通知→台账可见 | e2e/22-feedback-loop | 引擎 writeback、通知、runtime-ui 台账 |
| J5 | 界面标签不说谎（已发布≠未保存、配置完整≠标红） | e2e/23-ui-truthfulness | studio 编辑器、发布向导 |
| **J8** | **数据集物化→看板图表消费端**（区域汇总 150/200 断言） | e2e/24-dataset-chart | record、dataflow-sql、chart-data、AmisRenderer |

**冒烟套件 = J1+J2+J3+J4+J5**（`pnpm test:e2e:smoke`，15 用例实测 ~16s）。J8 为第二环（数据集/图表改动时必跑）。

## 二、影响矩阵（改了 X → 必跑哪些）

**全局规则**：① 拿不准先跑冒烟（16s），绿了再按行加跑；② 纯前端样式/文案 → J5+走查即可；③ 改 G3 校验器要双向验（非法被拦 + 合法仍放行）。

| 改动的模块 | 必跑 | 耦合原因 |
|---|---|---|
| ⚠️ **shared 类型契约** | **全量 e2e + 全部单测** | 跨层 DTO SSOT，改一处涟漪全仓 |
| ⚠️ **auth / 租户 / ALS 注入 / Prisma $extends** | **全量**（最低 J1+冒烟） | 租户隔离横切所有旅程 |
| object / record（字段/校验/Formula/Rollup/批量） | J2、J3、J4 | 记录是主链路的血液 |
| 流程引擎（执行器/completeTask/聚合/条件分支） | J3、J4（+J7 涉触发入口） | 多模式审批聚合与回写决策 |
| writeback / 通知节点 / runtime-ui（任务中心/台账） | J4（+ 邮件渠道单测 notification-executor-email.spec） | 反馈环三断言 |
| review / 版本模型 / 发布 / 环境指针 | J5、J6（+ e2e/09、18） | 治理链与环境隔离 |
| dataset / dataflow-sql / chart-data | **J8** + e2e/07 | 报表腿；SQL 下推改动重点看 J8 与 07 |
| open-api / X-API-Key | J7 | headless 形态 |
| studio 编辑器（画布/序列化器/配置面板） | J5 + **GUI 黑盒走查**（AGENTS.md QA 走查约定） | "标签说谎"类缺陷聚集地 |
| MCP / 方言指南 / G3 校验器 | J6 + 校验器单测 + 一次 MCP 生成冒烟 | AI 生成入口；校验器要双向验 |
| 连接器（HTTP 出站/webhook） | e2e/06（http_request 节点相关加 J3） | 流程节点引用连接器 |
| 云函数（isolated-vm/runner） | e2e/08（流程节点相关加 J3） | cloud_function 执行器 |
| 页面搭建器 / amis 渲染 | e2e/03、10 + 运行时手工开一页 | 表单页是 J3/J4 入口面 |
| ⚠️ **DB 迁移（prisma schema）** | **全量 + 本地 migrate 重放** | 数据层涟漪不可预测 |

## 三、2026-10-06 缺口清偿记录

| 缺口 | 状态 | 覆盖 |
|---|---|---|
| ① 数据集物化→图表消费端无 journey | ✅ e2e/24 | 物化断言（华东150/华北200）+ chart-data 响应断言 + canvas 渲染 |
| ② 通知渠道仅 IN_APP 有断言 | ✅ notification-executor-email.spec（网关单测） | 渲染+分派+降级边界；SMTP 传输本身归 nodemailer；顺带修 EMAIL 空收件人语义（跳过发送、success=false，与 IN_APP/WEBHOOK 一致） |
| ③ 会签驳回聚合分支 | ✅ e2e/16 新用例 | 任一拒绝立即取消兄弟任务；**并取证一个语义现状**：驳回无驳回边时令牌继续走下游（种子流程驳回的合同仍流向终审）——**待产品裁决**（A 现状靠条件边 / B 驳回即终止 / C 流程补驳回边），用例已按现状记录并标注 |

## 四、三层分工与边界（诚实说明）

- **单测**（gateway 749 等）：器官级正确性，秒级，改哪跑哪；
- **冒烟 e2e**（J1-J5，16s）：推送前确认**脊柱未断**——回答"系统还能用吗"，不回答"每个功能都对吗"；
- **全量 e2e**（CI，24 个 spec）：器官间关节全覆盖，PR 合并前兜底。

冒烟保不了的：视觉审美、业务规则正确性（业务方裁决）、未写断言的新缺陷类别。新缺陷类别出现时（如本轮"标签说谎"），**先转成不变量断言再修**。

## 五、运行命令

```bash
pnpm test:e2e:smoke   # 推送前/改动后快速确认脊柱（~16s，需本地服务在跑）
pnpm test:e2e         # 全量（CI 强制）
```
