## 二、缺陷与观察项清单

### D-NEW-1（P2，已修复+回归）移动到分组「清空则移入未分组」承诺不生效

- **症状**：移动 Modal 清空目标分组提交 → Modal 关闭、toast「应用已移动到新分组」，但应用仍在原组（no-op）。
- **根因**（代码定位）：`useAppCrud.ts` moveMutation 走 `appsApi.update(appId, { group: group || undefined })`——清空时 `undefined` 被 JSON 序列化丢弃，PUT 部分更新语义下字段不生效；而弹窗文案承诺「清空则移入未分组」。真正支持置空的 `PATCH /apps/groups`（to 空→group:null）未被该路径使用。
- **对照实验**：API `PATCH /apps/groups {from:"QA回归组2",to:""}` → `{ok:true,updated:1}` 生效；同操作 UI 路径 no-op。
- **次生问题（P3，登记未修）**：同组提交（updated=0）也弹「应用已移动到新分组」，误导性成功反馈；update 端点不返回 updated 数，修复需改造返回契约，登记第二轮。
- **修复**：`apps.ts` update 参数 `Omit<Partial<CreateAppRequest>,'group'> & { group?: string | null }`（直接交叉会取交集消掉 null，已注释）+ `useAppCrud.ts` 改传 `{ group: group || null }`（后端 @IsOptional 跳过 null、service 透传 Prisma 置 NULL）。
- **回归**：typecheck 0 错/studio 单测 176 全绿/GUI 实测清空→卡片落未分组（截图 `qa_fix_dnew1_moved_to_ungrouped.png`）。

## 三、执行失误披露（诚实纪律）

1. **18 字段加错对象**：创建 qa_lookup_target_r2 后 UI 焦点停留新对象，18 字段全部加到了目标对象（fields=24）；发现后 SQL 拆分归位。
2. **修数据顺序失误丢失字段定义**：拆分 UPDATE 先裁后加，18 字段 config 被删（测试自建数据无业务损失）；未先备份即执行破坏性 UPDATE 是纪律违反。此后按 GUI 权威形状（field-config/utils.ts buildConfig）用 API 重建并验证（ORD-0001 生成）。
3. **两次无效测试自我纠正**：超长校验误判（"长"*51 实为 51 字符合法放行，重测 101 字符 400 正确）；搜索未过滤误判（回车未按，提交后过滤正常）。
